# 记账软件产品与技术设计

## 1. 目标

做一个自己可控、长期可维护的记账软件，优先保证数据不丢、账目可查、迁移方便。第一版先服务个人使用，重点支持 iPhone 记账，同时让 Mac 可以查看、录入和导出。

核心目标：

- 记一笔账要快，最好 3 秒内完成常见支出录入。
- 数据默认保存在本机，离线也能完整使用。
- 支持 iPhone 和 Mac 通过同一个 Apple ID 同步。
- 每条账目都可以追溯编辑历史，避免误删或同步冲突导致数据消失。
- 能随时导出 CSV / JSON / SQLite 备份，未来换软件也能拿走数据。

非目标：

- 第一版不做多人共享账本。
- 第一版不做复杂企业会计。
- 第一版不依赖第三方后端服务器。
- 第一版不接入银行卡自动抓取，避免隐私、稳定性和合规问题。

## 2. 推荐技术路线

建议做一个 Apple 生态原生应用：

- UI：SwiftUI
- 平台：iOS + macOS
- 本地数据库：SQLite，推荐使用 GRDB
- 同步：CloudKit 私有数据库
- 备份：本地导出 + iCloud Drive 自动备份文件
- 图表：Swift Charts
- 安全：Face ID / Touch ID 解锁，数据库文件使用系统文件保护；后续可考虑 SQLCipher

为什么不建议第一版直接用 Web / React Native：

- 你的主要设备是 iPhone，原生输入、Face ID、CloudKit、后台任务、文件备份更顺。
- Mac 也可以用 SwiftUI 共用大量代码。
- 不需要维护自己的服务器，数据隐私和长期成本更可控。

## 3. 产品结构

应用分成五个主要区域：

1. 记账
2. 明细
3. 统计
4. 资产
5. 设置

### 3.1 记账

这是打开应用后的主入口。

必备能力：

- 快速选择支出、收入、转账。
- 一键截图识别金额，并把最可能的金额默认填入记账页。
- 输入金额。
- 选择账户。
- 选择分类。
- 自动填入当前时间。
- 可选填写备注、标签、商家、图片附件。
- 支持常用模板，例如“午饭”“打车”“咖啡”“房租”。

第一版要避免过度设计。常见支出路径应该是：

打开应用 -> 输入金额 -> 点分类 -> 保存。

更快的路径应该是：

按快捷按钮 -> 自动截图和识别金额 -> 打开已填金额的确认页 -> 用户接受或修改 -> 保存。

#### 3.1.1 截图识别快速记账

这个功能的目标是让用户不用手动输入数字。

触发方式：

- iPhone Action Button。
- 锁屏快捷指令。
- 桌面快捷指令。
- 分享截图到记账 App。
- Mac 菜单栏按钮或快捷键。

iPhone 推荐流程：

1. 用户停留在支付、订单、银行、外卖、聊天等页面。
2. 用户主动按快捷按钮。
3. 系统截图。
4. 截图交给记账 App 或 App Intent。
5. App 使用 OCR 识别截图里的文字和数字。
6. App 从候选数字里选择一个最可能的金额。
7. App 打开记账确认页，并默认填入这个金额。
8. 用户可以直接保存，也可以改金额、分类、账户后保存。
9. 用户取消时，不创建正式账目。

确认页默认值：

- 金额：OCR 选出的最可能金额。
- 类型：默认支出。
- 账户：最近常用账户，或用户设置的默认账户。
- 分类：根据商家、页面文字、历史习惯推断；无法判断时使用“未分类”。
- 时间：当前时间。
- 备注：可自动填入识别到的商家或订单关键词。
- 附件：可选择保存原截图，第一版默认不保存，避免隐私风险。

金额选择规则：

- 优先选择带有货币符号、`实付`、`支付`、`合计`、`总计`、`金额`、`付款` 附近的数字。
- 避免选择订单号、手机号、时间、日期、余额、积分、卡号、验证码。
- 如果出现 `原价`、`优惠`、`实付`，优先选择 `实付`。
- 如果有多个候选金额，默认填入置信度最高的金额，并在确认页显示其他候选。
- 如果置信度低，不要自动保存，只打开确认页并提示“请确认金额”。

安全规则：

- 截图识别只能生成待确认草稿，不能直接写入正式账目。
- 只有用户点保存后，才创建 Transaction。
- 用户取消时，草稿和截图都应删除。
- OCR 结果不要作为事实保存进账本，只保存用户确认后的金额。
- 如果保存截图附件，必须让用户明确选择。

### 3.2 明细

明细是账目的可靠查询入口。

必备能力：

- 按时间倒序显示账目。
- 按月份分组。
- 搜索备注、分类、账户、标签。
- 筛选支出 / 收入 / 转账。
- 筛选账户。
- 筛选分类。
- 点开账目查看详情和修改历史。

关键要求：

- 删除不是立刻物理删除，而是进入回收站。
- 编辑账目时保留旧版本记录。
- 转账必须作为一笔完整操作展示，不能显示成两条互相独立的账。

### 3.3 统计

统计用于回答“钱花到哪里了”。

第一版统计：

- 本月支出总额。
- 本月收入总额。
- 本月结余。
- 按分类统计支出。
- 按账户统计余额。
- 月度趋势。

第二版统计：

- 分类预算。
- 同比 / 环比。
- 大额支出提醒。
- 订阅和固定支出识别。
- 自定义报表。

### 3.4 资产

资产区管理钱在哪些账户里。

账户类型：

- 现金
- 借记卡
- 信用卡
- 支付宝 / 微信
- 投资账户
- 其他

第一版不要自动计算投资盈亏，只记录账户余额和流水。投资、股票、基金这类复杂资产可以后续单独设计。

### 3.5 设置

设置区承担数据安全和迁移能力。

必备能力：

- iCloud 同步开关和同步状态。
- 手动备份。
- 自动备份设置。
- 导出 CSV。
- 导出 JSON。
- 导出 SQLite 数据库。
- 从备份恢复。
- 回收站。
- Face ID / Touch ID 解锁。
- 分类管理。
- 账户管理。

## 4. 核心数据逻辑

这类软件最怕“看起来记上了，但余额错了”或者“同步后某笔账没了”。所以底层应该使用类似流水账的结构，而不是只在账户上存一个余额数字。

### 4.1 基本原则

- 账目是事实记录。
- 账户余额由账目计算出来。
- 每次修改都留下历史。
- 删除先软删除，不直接移除数据库行。
- 同步只同步结构化数据，不同步界面临时状态。

### 4.2 账目类型

账目分三类：

- 支出：从一个账户流出，归到一个支出分类。
- 收入：进入一个账户，归到一个收入分类。
- 转账：从一个账户流出，进入另一个账户，不计入支出或收入。

### 4.3 推荐数据模型

#### Account

账户表示钱所在的位置。

字段：

- id
- name
- type
- currency
- openingBalance
- sortOrder
- isArchived
- createdAt
- updatedAt
- deletedAt

#### Category

分类表示钱的用途或来源。

字段：

- id
- presetKey
- name
- kind: expense / income
- parentId
- icon
- color
- sortOrder
- isSystemPreset
- isArchived
- createdAt
- updatedAt
- deletedAt

规则：

- kind 决定分类只能用于支出或收入，不能混用。
- 转账不使用分类。
- parentId 用于二级分类，第一版可以只展示一级分类，先保留字段。
- presetKey 用于识别系统预设分类，方便升级时补充新分类。
- isSystemPreset 表示系统默认分类。用户可以改名、改图标、改排序、归档，但不建议物理删除。
- 已经被账目使用过的分类不能直接删除，只能归档。

#### 默认分类预设

预设分类的目标是让用户第一次打开应用就能直接记账，不需要先搭分类。

设计原则：

- 支出分类优先覆盖高频生活场景。
- 收入分类要区分工资、奖金、副业、投资、报销、退款这几类常见来源。
- 每个分类都有默认图标和颜色，界面上用图标优先识别，文字作为辅助。
- 预设分类不能太多，第一版保持在一屏左右，后续允许用户自己添加。
- 必须有“其他支出”和“其他收入”，避免用户因为找不到分类而不能保存。

支出预设：

| presetKey | 名称 | 图标 | 用途 |
| --- | --- | --- | --- |
| expense_food | 餐饮 | fork.knife | 正餐、外卖、饮品 |
| expense_transport | 交通 | tram.fill | 地铁、公交、打车 |
| expense_daily | 日用 | basket.fill | 超市、生活用品 |
| expense_shopping | 购物 | bag.fill | 衣物、电子产品、网购 |

| expense_entertainment | 娱乐 | gamecontroller.fill | 电影、游戏、聚会 |
| expense_health | 医疗 | cross.case.fill | 看病、药品、体检 |
| expense_education | 学习 | book.fill | 课程、书籍、培训 |
| expense_family | 家庭 | person.2.fill | 家人相关支出、人情往来 |
| expense_other | 其他支出 | ellipsis.circle.fill | 无法归类的支出 |

收入预设：

| presetKey | 名称 | 图标 | 用途 |
| --- | --- | --- | --- |
| income_salary | 工资 | banknote.fill | 固定工资、薪水 |
| income_bonus | 奖金 | gift.fill | 年终奖、绩效、奖励 |

| income_refund | 退款 | arrow.uturn.left.circle.fill | 退货退款、订单取消返款 |
| income_transfer_in | 转入调整 | arrow.down.left.circle.fill | 余额校正、非收入性质流入 |
| income_gift | 礼金 | envelope.fill | 红包、礼物、礼金 |
| income_sale | 闲置出售 | shippingbox.fill | 二手出售、闲置物品回款 |
| income_other | 其他收入 | ellipsis.circle.fill | 无法归类的收入 |

默认展示规则：

- 记支出时只显示支出分类。
- 记收入时只显示收入分类。
- 常用分类排在前面，排序依据是最近 30 天使用次数。
- 新用户没有历史记录时，支出默认顺序是餐饮、交通、日用、购物、订阅、娱乐。
- 新用户没有历史记录时，收入默认顺序是工资、副业、奖金、报销、退款。
- OCR 快速记账默认进入支出模式，优先从支出分类里推荐。
- 退款识别到“退款”“退回”“原路返回”时，优先建议收入分类“退款”，但仍让用户确认。

分类管理规则：

- 用户可以新增自定义分类。
- 用户可以把预设分类改名，例如把“餐饮”改成“吃饭”。
- 用户可以隐藏不用的分类，隐藏后不在记账页默认显示。
- 隐藏分类不影响历史账目展示。
- 不能删除“其他支出”和“其他收入”。
- 导入旧数据时，如果旧分类不存在，应自动创建自定义分类，而不是强行归入“其他”。

#### Transaction

Transaction 表示用户看到的一笔账。

字段：

- id
- kind: expense / income / transfer
- amount
- currency
- accountId
- toAccountId
- categoryId
- occurredAt
- note
- merchant
- tags
- attachmentIds
- createdAt
- updatedAt
- deletedAt
- revision

规则：

- 支出必须有 accountId 和 expense categoryId。
- 收入必须有 accountId 和 income categoryId。
- 转账必须有 accountId 和 toAccountId，不能有 categoryId。
- amount 必须大于 0。
- accountId 和 toAccountId 不能相同。

#### TransactionRevision

记录每次账目修改前后的内容。

字段：

- id
- transactionId
- changedAt
- changeReason
- beforeJson
- afterJson

用途：

- 查清楚什么时候改过。
- 恢复误改。
- 排查同步冲突。

#### QuickEntryDraft

快速记账草稿表示 OCR 或快捷指令生成的待确认内容。它不是正式账目。

字段：

- id
- source: screenshot / share / camera / manualShortcut
- candidateAmount
- candidateAmounts
- suggestedKind
- suggestedAccountId
- suggestedCategoryId
- suggestedMerchant
- recognizedTextPreview
- confidence
- createdAt
- expiresAt

规则：

- QuickEntryDraft 不参与余额计算。
- QuickEntryDraft 不进入明细列表。
- 用户点保存时，才把草稿转换成 Transaction。
- 用户取消或草稿过期时，直接删除草稿。
- 草稿默认不上传 CloudKit，因为它只是当前设备上的临时操作。

#### Attachment

保存票据、截图等附件。

字段：

- id
- transactionId
- localFileName
- cloudAssetId
- createdAt
- deletedAt

第一版附件可以只做本机保存，等账目同步稳定后再做 CloudKit 附件同步。

#### RecurringRule

周期账单规则，例如房租、会员订阅。

字段：

- id
- name
- templateTransactionJson
- frequency
- nextRunAt
- isActive
- createdAt
- updatedAt

### 4.4 余额计算

账户余额不要手动维护为唯一事实来源。正确做法：

账户余额 = 初始余额 + 收入流入 - 支出流出 + 转账流入 - 转账流出。

为了性能，可以缓存余额，但缓存必须能从账目重新计算。

### 4.5 删除策略

删除分两层：

1. 普通删除：设置 deletedAt，账目进入回收站。
2. 永久删除：只允许在回收站里手动执行，并且执行前生成备份。

第一版可以不提供永久删除，只提供回收站和恢复。

## 5. 同步与备份设计

### 5.1 本地优先

本地 SQLite 是主工作区。用户离线时仍然可以完整记账、编辑、搜索和统计。

同步只是把本地变更复制到 iCloud，并把其他设备的变更拉下来。

### 5.2 CloudKit 同步

每个主要对象都使用稳定 id：

- Account
- Category
- Transaction
- TransactionRevision
- RecurringRule

同步字段：

- id
- updatedAt
- deletedAt
- revision

冲突处理：

- 不同字段的普通文本改动可以用较新的 updatedAt 覆盖。
- 金额、账户、分类、时间这类关键字段发生冲突时，不要自动静默合并。
- 同一笔账在两台设备被同时编辑时，保留两个版本，并在明细里提示“有冲突需要确认”。

### 5.3 备份

备份要比同步更重要。同步不是备份，因为同步会把错误也同步过去。

建议：

- 每天自动生成一个 JSON 备份。
- 每周自动生成一个 SQLite 完整备份。
- 备份文件保存到 iCloud Drive 的应用目录。
- 保留最近 30 天日备份。
- 保留最近 12 个周备份。
- 手动备份永不自动删除。

恢复流程：

1. 用户选择备份文件。
2. 应用先检查备份版本和完整性。
3. 当前数据库自动另存一份安全副本。
4. 导入备份。
5. 重新计算余额。
6. 展示恢复结果。

## 8. 数据安全底线

必须坚持这些规则：

- 保存账目前先校验金额、账户、分类。
- 保存和编辑使用数据库事务。
- 不直接物理删除账目。
- 每次启动检查数据库版本。
- 每次恢复备份前先备份当前数据库。
- 余额可以缓存，但必须能重新计算。
- 导入数据不能覆盖现有数据，除非用户明确选择恢复模式。
- 同步冲突不能静默覆盖金额、账户、分类、时间。

## 9. 开发顺序建议

1. 建立 SwiftUI 多平台项目。
2. 接入 SQLite / GRDB。
3. 定义 Account、Category、Transaction 三个核心表。
4. 写本地数据库迁移。
5. 做 iPhone 记账页。
6. 做明细页。
7. 做余额计算和月度统计。
8. 做编辑、软删除、恢复。
9. 做导出和导入。
10. 做 Mac 三栏界面。
11. 做 CloudKit 同步。
12. 做自动备份。
13. 做周期账单、预算、附件。

## 10. 第一批测试用例

至少覆盖：

- 新增支出后，账户余额减少。
- 新增收入后，账户余额增加。
- 新增转账后，一个账户减少，另一个账户增加，总资产不变。
- 截图里只有一个明显金额时，快速记账草稿默认填入该金额。
- 截图里有多个金额时，草稿默认填入最可能金额，并保留其他候选供用户选择。
- 用户取消快速记账草稿后，不创建正式账目。
- 用户接受快速记账草稿后，才创建正式账目。
- 修改支出金额后，余额重新计算正确。
- 删除账目后，默认明细不显示，回收站显示。
- 恢复账目后，余额重新计算正确。
- 导出再导入后，账目数量和余额一致。
- 空分类不能保存支出或收入。
- 转账不能选择同一个账户。
- 同步冲突不会直接覆盖关键字段。

## 13. 最重要的取舍

这个软件的第一原则不是功能多，而是数据可靠。

所以第一版应该先把本地数据库、软删除、导出、恢复、余额重算做好。只要这几件事情可靠，即使同步或图表晚一点做，也不会再回到“软件不能用，数据也没了”的状态。
